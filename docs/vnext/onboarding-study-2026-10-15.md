# Existing-repository onboarding study: first research pass

Date: 2026-10-15  
Status: Desk research, local synthetic rehearsal, and a public-repository technical pilot. No real pilot user, repository approval, actual coding-agent session, or competitor account trial is claimed.

Implementation update: `anvilmark start` now composes repository inventory and user-described local draft creation in one command, with safe resume. An explicit `--connect-codex` adds a project-scoped MCP connection for agent drafting, leaving existing settings intact and prompting for write tools. The command has fixture tests, a public-repository technical run, and a local tarball installation in a clean temporary directory. Registry distribution, actual Codex tool use, and an unaided real user trial remain open. The baseline observations below describe the path before these slices.

This study begins R1 in the [ten-node workflow plan](10-node-workflow-plan.md). The project owner chose **an existing AI-enabled repository** as the first entry path and then selected a public example for the first technical pilot. A user-owned pilot repository and actual user trial are still needed.

## Question

How can a developer begin in an existing AI-enabled repository and obtain a source-linked, editable Anvilmark decision brief with little setup, no manual transfer of project data among interfaces, and no silent promotion of agent guesses into policy?

The first useful result is an inventory, draft brief, and visible gaps. It is not an approved decision or a compliance verdict. A full model-quality decision may require a separate measured evaluation.

## What the current Anvilmark path requires

The [Quickstart](../../QUICKSTART.md), [CLI guide](../../packages/cli/README.md), and [MCP guide](../../packages/mcp/README.md) describe a checkout-based installation with Node 24 and pnpm 11.16.0. A real project then needs contract initialization and elicitation, optional agent configuration or request export/import, candidate/evidence work, human approval, repository scan declarations, and conformance. The workshop fills many of these inputs with synthetic Atlas material; it is a training path, not an automatic real-repository assessment.

| Boundary         | Current behavior                                                                                                                    | First-run friction to test                                                                  |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Install          | Clone checkout, install dependencies, build packages; npm packaging scripts exist but clean release/install verification is open    | Runtime/package-manager setup, time and failure recovery                                    |
| Project start    | CLI init, elicitation and edits; browser can export a draft for CLI import                                                          | Repeated entry of repository facts and browser-to-CLI transfer                              |

| Evidence         | Public research and manually refreshed catalog; project-specific measured evaluation still required for a hard quality gate         | Candidate identity mapping and access to a labelled workload                                |

### Local rehearsal performed

- Environment shell: Node 25.7.0 and pnpm 11.16.0. The documented supported Node 24.13.1 binary was available separately. This environment should not be counted as an unaided fresh install.
- The doctor run under Node 25 rejected the unsupported Node version. Under Node 24 it accepted Node, dependencies, CLI, and project-MCP entry points but failed its pnpm subprocess check. A direct shell pnpm version check succeeded; a diagnostic Node spawn returned an EPERM error in this sandbox. This is an environment-limited observation, not evidence of a general Anvilmark packaging defect.
- The existing Atlas workshop was run with the Node 24 binary in a fresh directory under /tmp. It completed in 7.49 seconds of process time and produced a proposed **synthetic** decision and printed review/approval/check commands. No approval was entered, no agent was launched, and no real model/provider evidence was collected. The elapsed process time does not include installation, reading, review, evaluation, or integration with a real application.
- The workshop output required a later terminal review and approval, followed by a check. MCP client configuration was printed as an optional manual command. This is useful for testing the checker but does not yet satisfy the no-transfer, agent-first product goal.

## Public repository technical pilot

The project owner chose a public example for this first trial. I cloned [openai/openai-responses-starter-app](https://github.com/openai/openai-responses-starter-app) into `/tmp` and checked out commit `0fae283f12ca3f71015cd9fa3f9b28df97e9ae21`, already present in the [hand-labelled benchmark](../../benchmarks/real-repos/repos/openai-responses-starter-app.json). This is a technical test by the implementer, not an unaided first-user study. The earlier benchmark labels are useful comparison data but are not independent new labels.

| State                                                                 | `anvilmark start` process time | Recognized labelled AI calls | What happened                                                                                                                                                                                                                               |
| --------------------------------------------------------------------- | -----------------------------: | ---------------------------: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Before app dependency install                                         |                         1.23 s |                       1 of 7 | Six OpenAI SDK calls stayed unresolved or uncertain; the raw HTTP call was found. The command created no project because no description was supplied.                                                                                       |
| After `npm ci --ignore-scripts --no-audit --no-fund`                  |                         3.08 s |                       7 of 7 | All seven pre-labelled calls appeared at their labelled file and line, including inference, upload, management, and raw HTTP. Two unrelated network hops remained uncertain.                                                                |
| From a nested route directory, with a pilot-only operator description |                         2.95 s |                       7 of 7 | `start` found the Git root, created `.anvilmark/project.yaml` there at revision 1, and recorded only the supplied description and repository reference. A second run reported the existing project and left the contract SHA-256 unchanged. |

The app dependency install used the network, added 624 packages in about ten seconds, and disabled package scripts. Anvilmark itself made no network or model call and did not read an API key value. The post-install scan still reported 204 overall unknowns, two specifically about AI calls, endpoints, models, or SDKs; it did not claim complete coverage or conformance. The high overall unknown count may distract from the two relevant unresolved network locations and needs a comprehension test.

**Setup decision from this trial:** keep installation of the app's own dependencies separate from Anvilmark, but explain when missing SDK packages can hide calls. The inventory now gives that guidance if imports are unresolved. This trial supports the one-command local entry on a prepared repository; it does not verify a published-package or unaided installation, source-cited extraction from decision documents, human review time, agent consumption, or a GitHub PR check. No approval or hard rule was created for the public app.

### Local package installation check

The current checkout built a six-file, 452 KB npm tarball. I installed that tarball with scripts disabled into a fresh `/tmp` prefix; npm installed seven packages in about one second. Its `anvilmark` binary ran `start` on the public app in 3.16 seconds, found the same seven calls, and resumed the existing draft. The same packaged CLI also worked under the documented Node 24.13.1 runtime in 3.23 seconds. This verifies the built package path in this one environment. It does not verify a published registry package, an unaided developer installation, other operating systems, or a PR workflow.

### Project Codex connection check

[Codex's current MCP guide](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) documents project-scoped `.codex/config.toml`, stdio `command`/`args`/`cwd`, and `default_tools_approval_mode = "writes"`. Its [configuration guide](https://learn.chatgpt.com/docs/config-file/config-basic) says project settings load only for trusted projects. On that basis, `start --connect-codex` is opt-in and writes only this repository's `.codex/config.toml`; it does not edit the global Codex file. It enables the existing `--agent-assessment` MCP tools and sets write-tool prompting. The generated block uses absolute paths to the installed server and project, so it needs reconnection after either moves.

A fresh local tarball installation ran `start --connect-codex` from a nested directory in the public pilot. The resulting TOML parsed and pointed to an existing packaged server and the correct repository. A direct stdio initialize and tools/list exchange with that packaged server advertised `draft_decision_brief` as a writing tool and `compare_decision_options` as read-only. Unit tests cover preserving unrelated Codex settings, idempotence, refusing an existing Anvilmark entry, and rejecting a config symlink. This is a configuration/protocol smoke test, not evidence that a running Codex agent retrieved context, drafted a cited decision, or that the approval prompt appeared in its UI. Those remain real-pilot tests.

### PR gate finding

The public app has a description but no approved decision or conformance rules, so it cannot be a meaningful passing PR check. During gate review, I found that the conformance summary previously counted an empty rule set as compliant. The local checker now writes a `NOT EVALUATED` report, records `compliant: false`, and exits 2 when no rule is configured. A regression test covers that case. A PR gate must run normal `conformance`, not `conformance --check`, because the latter only verifies that a stored report is current. It also needs a trusted base revision for its contract, scanner declarations, and workflow; otherwise a PR could remove its own checks. A released, pinned Anvilmark package and a repository with a reviewed rule remain prerequisites for an end-to-end trial.

**Inference from the sources:** easy agent wiring, architecture drafts, and PR checks are already documented in adjacent products. Anvilmark's proposed advantage needs to be demonstrated through the _same approved decision_ spanning workload-specific evidence, model/provider/deployment choice, and source conformance. Public pages cannot prove that no other product does this; the [hands-on matrix](02-competitor-hands-on-matrix.md) records what was actually tested and what remains gated.

## Research inputs to test, not adopt blindly

- [CIAO: Code In Architecture Out](https://arxiv.org/abs/2604.08293) proposes repository-to-architecture documentation and reports a study with contributors. Anvilmark should test whether its suggested nodes and edges are correct, source-linked, and reviewable for the pilot, especially data boundaries.
- [R2Code](https://arxiv.org/abs/2604.22432) studies requirements-to-code links. Anvilmark should compare an agent's proposed links against explicit file/component mappings and independent labels, including abstention when the link is uncertain.
- [Software Reflexion Models](https://www.cs.ubc.ca/~murphy/papers/rm/fse95.html) compares declared architecture with observed source relationships. The initial review view can distinguish declared, observed, divergent, and unmapped relationships rather than collapsing everything into compliance.

None of these papers establishes that an LLM can safely infer a company's binding privacy policy from repository prose. Exact quotation and human confirmation remain separate from policy authority.

## R1 experiment ready for the first real pilot

1. Freeze the pilot repository commit, selected AI-related change, current ADRs, and a source-disclosure policy. Label at least one known AI call, one decision document claim, one ambiguity, and one possible violation before running Anvilmark.
2. Run **A: current documented path** with an engineer new to this project. Time from working installation to first source-linked inventory/draft. Record commands, files touched, questions, transfers, and errors.
3. Run **B: agent-assisted path** on a fresh copy of the same commit. The agent may propose claims with exact excerpts; independently verify every cited claim and every proposed hard constraint. Do not let the agent approve.
4. Compare with competitor-documented flows only at the level observed above. A fair hands-on comparison needs the same repository, permissions, input, and access; mark unavailable product paths as gated.
5. Have a second reviewer inspect the resulting draft without seeing which path produced it. Measure omitted workloads, wrong claims, unsupported hard rules, source-link precision, time to correction, and whether the draft changes candidate exclusions.
6. Choose the setup design only after reviewing both its speed and error costs. A faster path that creates false hard constraints fails the product goal.
